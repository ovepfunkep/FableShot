# FableShot — уведомления, восстановление и онлайн-комнаты

План от 24 ноября 2026 года для React Android и PWA. Проектирование — GPT‑6.2 Sol Ultra. Основные шаги реализации — Sol Medium. Для проверки доступа к копиям, восстановления после сбоя и гонок финализации комнаты — Sol High.

## Порядок разработки

1. **Пакет A1. Уведомления Android.** GitHub Actions вызывает FCM после готовности APK и PWA. Отдельный выпуск, независимый от облачного дневника.
2. **Пакет B0. Общий облачный контур.** Пилот Auth, базы, приватного хранилища и серверных функций. Проверить доступ с устройств и сетей, которыми пользуются лучники.
3. **Пакеты A2 и B1. Web Push и восстановление.** После B0 подписки веб-устройств и резервирование можно разрабатывать параллельно. Оба пакета можно выпускать отдельно за флагами.
4. **Пакет C. Онлайн-комната.** Переиспользовать интерфейс и правила локальной комнаты. После B0 вести параллельно с восстановлением, общий контракт входа принять до реализации обеих функций.

Обычные тренировки, импорт и статистика продолжают открываться без входа и работать офлайн. Публичный сайт и APK остаются на GitHub. Облачные функции подключаются в приложении по выбранному сценарию. Для пилота нужен управляемый сервис, без аренды и обслуживания отдельной виртуальной машины.

## A1. Push о новых версиях на Android · Medium

**Сценарий.** Лучник разрешает уведомления об обновлениях один раз. После выпуска видит «Доступен FableShot 0.30.30» и открывает знакомое «Что нового». Для экрана блокировки использовать одну короткую строку, актуальный номер версии и системный значок приложения.

1. В `web/src/android-updates.ts` оставить существующий `versionCode` и проверку GitHub Releases источником истины для доступности APK. Добавить отдельный Capacitor-мост в `web/native/android/` и подключить его к продуктивному React-пакету через `web/scripts/build-android.ps1`. Тестовый пакет и dev-сборка используют отдельную тему либо заглушку. Добавить в «Настройки → Уведомления» тумблер «Обновления». По умолчанию выключен. Первый тап запрашивает системное разрешение, после разрешения подписывает устройство на публичную тему `fableshot_stable_updates`. Выключение отписывает; при возвращении системного разрешения сверить локальный выбор и подписку. Без Google Play Services остаётся проверка при входе на Главную. [Разрешения и требования FCM на Android](https://firebase.google.com/docs/cloud-messaging/android/get-started) · [Подписки на темы FCM](https://firebase.google.com/docs/cloud-messaging/manage-topic-subscriptions)
2. Добавить отправку в `.github/workflows/pages.yml` **после** успешного `publish-android`, который уже зависит от успешной публикации Pages. Отправитель проверяет стабильный тег, код и ожидаемый опубликованный APK. Для идентификации GitHub Actions у FCM использовать ограниченный service account с короткоживущим доступом через Workload Identity Federation, привязанный к репозиторию и релизному workflow. Не помещать отправительские полномочия в APK или PWA. Тест рассылки идёт отдельным запуском на тестовую тему. [Workload Identity Federation для CI](https://cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines) · [Триггеры и `GITHUB_TOKEN`](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
3. Передавать данные `type=release`, `version`, `versionCode` и показывать уведомление своим обработчиком `FirebaseMessagingService`, который может сверить код установленной версии и разрешение. Ключ показа `release-${versionCode}`, одинаковый при повторе, TTL 72 часа, системный канал «Обновления». Уже установленную или ранее показанную версию приложение отсекает по коду. При активной тренировке пуш остаётся в системной шторке, при открытии по тапу «Что нового» откладывается до выхода с экрана ввода. По тапу сверить релиз и показать накопленные изменения по существующим правилам. Скачать APK можно явной кнопкой. Один стабильный релиз — одно уведомление на устройство. Неудачная рассылка явно видна в CI и повторяется отдельным действием для той же версии. APK и сайт остаются доступными.
4. **Приёмка.** Разрешил, отказал, отписался, повторно подписался, телефон без сервисов Google, приложение занято тренировкой, версия уже установлена, повторный запуск отправки, черновик или сбой Pages. Проверить реальную доставку на Android в фоне и переход по тапу. Проверки `android-updates` дополнить обработкой кода и повторов. Системная доставка зависит от настроек телефона и сети.

## B0. Учётная запись и облачный контур · Medium, сверка доступа High

1. Опорный вариант пилота — управляемые Supabase Auth, Postgres, Storage и Realtime, серверные операции — транзакционные RPC или Edge Functions. Перед включением у пользователей проверить три вещи на реальных Android и iPhone плюс браузере ПК: HTTPS и WSS из сетей клуба, вход по почтовому коду, максимальный архив с вложением. Для public-пилота подключить собственный SMTP с подтверждённым отправителем. GitHub Pages хранит только публичную конфигурацию клиента и фронтенд. Предусмотреть отдельные окружения dev и pilot. [Вход по одноразовому коду](https://supabase.com/docs/guides/auth/auth-email-passwordless) · [SMTP](https://supabase.com/docs/guides/auth/auth-smtp) · [Тарифы и ограничения](https://supabase.com/pricing)
2. Стабильный аккаунт — адрес почты и одноразовый код из письма. Пользователь вводит код в том же приложении, поэтому переход между почтой, APK и PWA не требует deep link для входа. Гостю комнаты выдаётся внутренняя анонимная сессия, без почты, пароля и формы регистрации. Постоянный аккаунт требуется для облачной копии и создания интернет-комнаты, вход по приглашению доступен любому из двух типов. При подключении почты к гостю сначала проверять, принадлежит ли она уже другому аккаунту. Открытая комната сохраняет свою исходную личность до выхода, даже если пользователь затем входит в другой аккаунт. [Анонимный вход и связывание аккаунтов](https://supabase.com/docs/guides/auth/auth-anonymous)
3. В `web/src/` добавить облачный клиент по общему контракту, серверные миграции и функции хранить рядом в проекте, например в `supabase/`. Показать отдельные состояния «Нет сети», «Войти», «Код истёк», «Отправить повторно». Выход из аккаунта удаляет облачный сеанс на этом устройстве, локальный дневник остаётся доступным. Публичные запросы ограничены необходимыми операциями. Идентификатор владельца берётся из проверенного токена, гостевой статус из подтверждённых claims. RLS и тесты доступа обязательны для каждой таблицы или комнаты. Отдельные роли отправителя push, оператора метаданных и доступа к ключам. В технических журналах — коды ошибок и ID запросов, без кодов входа, приглашений, токенов и содержимого дневника.
4. **Пилот до оплаты и публичного включения.** Измерить средний и p95 размер ZIP на обезличенных примерах. Бюджет хранения `3 × число аккаунтов × средний размер` плюс незавершённые записи, исходящий трафик — копии при скачиваниях и восстановлении плюс обмены комнат. Например, 50 дневников по 10 МиБ с тремя версиями требуют около 1,5 ГиБ до накладных расходов. Проверить квоты проекта, лимит объекта, паузу при неактивности, почту, доступность и распределение расходов. Если лимита нет или сеть нестабильна, сохранить контракт и проверить другой управляемый вариант. Результат пилота фиксировать с конкретными замерами до подтверждения тарифа или публичного подключения.

## A2. Web Push для установленной PWA · Medium

1. Добавить кнопку «Уведомления об обновлениях» с тем же смыслом, что на Android. На iPhone показать «Добавь FableShot на экран „Домой“» при открытии обычной вкладки, запрашивать разрешение из установленной PWA после нажатия. На поддерживаемом Chromium запрос тоже идёт от явного действия. Для обеих платформ аккаунт для рассылки не нужен. Установленное Android-приложение использует только FCM, браузерный FableShot — Web Push. [Web Push в iOS и iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
2. В `web/scripts/build-offline.mjs` дописать обработчики `push` и `notificationclick` в текущий service worker. Сохранить precache, пути `/FableShot/` и обработку обновления офлайн-кэша. Подписка `PushManager` регистрируется добровольно, ID устройства и права на изменение выдаются сервером. В приватной таблице хранить endpoint, ключи подписки, время изменения и статус. Исходящая отправка — через стандартный Web Push с ключами VAPID, закрытый ключ хранится в секретах сервиса. Ограничить регистрацию форматом подписки, допустимыми HTTPS push-адресами и частотой, отозванные или истёкшие подписки удалять после ответа 404/410. Вход или выход из аккаунта поддержки push не меняет.
3. GitHub Actions после выпуска вызывает тот же логический запуск рассылки. Сервер хранит уникальный ключ `release.channel + versionCode` и состояние отправки для каждого получателя, отправляет пачками, временные ошибки повторяет с тем же ключом и сроком доставки. Service worker показывает одно уведомление с тегом версии. По тапу открыть существующую вкладку или PWA на `/FableShot/`, обновить клиент штатным способом и вывести «Что нового». Если сеть пропала, открыть офлайн-версию и предложить повторить обновление после подключения.
4. **Приёмка.** Chrome, установленная PWA на iPhone, отказ, отписка, отдельные установки на разных телефонах, устаревшая подписка, повтор CI, тап при открытом и закрытом приложении. Проверить, что изменения service worker сохраняют офлайн-открытие и подключение к онлайн-комнате после выхода из авиарежима.

## B1. Резервное копирование и восстановление · Medium, контроль транзакций и ключей High

**Сценарий.** Телефон сломался. На новом устройстве лучник выбирает «Восстановить дневник», входит по коду из почты, видит резервные версии и выбирает нужную. Достаточно доступа к аккаунту. На устройстве с существующей историей перед заменой видны число тренировок и стрел в обеих версиях и доступен локальный откат.

1. Переиспользовать `captureArchiveRecords`, `createWebArchive`, `inspectWebArchive`, связанный исходный Android ZIP и `replaceArchiveRecords` из `web/src/web-archive.ts`. Входы — `WebOnboarding.tsx` и `ArchiveScreen.tsx`. Дневник и рецепты чтения старого формата остаются в `app-storage.ts` и `indexed-journal.ts`. Удалить из облачного снимка живые полномочия и очередь комнаты, сохранить личный результат и уже полученный снимок итогов. Ручное восстановление ZIP остаётся рядом, доступно офлайн. Настройки разрешения push и облачный сеанс привязаны к устройству.
2. После добровольного подключения сохранить первую копию. Далее отмечать грязную ревизию после успешной локальной записи данных. Пока приложение открыто, загружать через 60 секунд после последнего изменения и не чаще раза в 10 минут. При потере сети попытаться после возвращения связи с ограниченной задержкой и при следующем открытии. «Создать копию сейчас» запускает немедленную попытку той же очереди. Для каждой попытки фиксировать ревизию и хеш архивных данных без плавающего времени создания ZIP. Новая правка во время передачи сохраняется как следующая грязная ревизия. Статус показывает «Последняя подтверждённая копия», дату, количество тренировок в последней доступной локальной сводке или «Ожидает сети». Закрытое приложение в первом пакете копию не обещает.
3. Поскольку для восстановления достаточно входа, доступ к расшифровке выдаёт сервис после проверки владельца. Использовать шифрованное соединение и приватное объектное хранилище. Для шифрования самого файла — AES-256-GCM с новым случайным ключом данных и 96-битным nonce на копию, ключ данных в каталоге хранить обёрнутым управляемым ключом. Версионировать формат и ID ключа, привязать шифротекст к владельцу, ID копии и формату через AAD. При создании копии функция выдаёт новый ключ данных, клиент шифрует ZIP перед выгрузкой. При восстановлении функция разворачивает сохранённый ключ только для владельца подтверждённой версии. ZIP и ключ открытым текстом в хранилище, логах и локальном хранилище настроек не класть. Сервис способен разрешить расшифровку по аккаунту, поэтому это шифрование копии с управляемыми ключами. [Конвертное шифрование и KMS](https://cloud.google.com/kms/docs/envelope-encryption)
4. Протокол `begin → upload → finalize`. `begin` создаёт неизменяемый ID попытки, условный номер головы каталога, лимит размера и краткоживущий доступ к объекту. Повтор передачи использует тот же ID. Загружать крупные образцы штатным возобновляемым протоколом, сборку и шифрование больших архивов вынести из UI-потока по результатам замеров. В `finalize` проверить объект, размер и контрольную сумму, затем одной операцией подтвердить новую версию и сменить голову по CAS. Хеш объекта проверяет доверенная сторона через поддерживаемую контрольную сумму хранилища или потоковое чтение; облачная функция в HTTP-пути не держит архив целиком в памяти. Успешный ответ относится к конкретной версии. Каталог держит три последние подтверждённые копии, очистка удаляет только устаревшие и незавершённые. При квоте, обрыве или истечении сеанса прежняя голова остаётся доступна. [Возобновляемая загрузка в Supabase Storage](https://supabase.com/docs/guides/storage/uploads/resumable-uploads)
5. **Два устройства.** В первом выпуске одно активное устройство создаёт облачные копии. На втором доступен список и восстановление. Команда «Создавать копии с этого устройства» показывает время и объём обеих записей и подтверждается отдельно. Пустая установка не имеет права автоматически стать новым источником. Если локальные данные на устройствах разошлись, предложить восстановить облачную версию или сохранить независимый ZIP перед сменой источника. На сервере сменить эпоху устройства записи и снять старое разрешение. В настройках дать «Отключить автокопии» и отдельное подтверждаемое «Удалить облачные копии». Ни одно из действий не меняет личные локальные записи.
6. **Восстановление.** После входа показать только подтверждённые версии владельца с датой, размером и отметкой устройства, без открытых ссылок на объект. Выбор скачивает защищённый файл, проверяет подпись AES-GCM и ZIP, показывает имеющийся предпросмотр. Последнее подтверждение применяет текущую атомарную замену с локальной копией для отката. Серверная несовместимая или повреждённая версия оставляет доступ к предыдущей. Существующие данные, награды и результаты после восстановления не запускают повторные поздравления и отправки. Обновить прежний [сценарий восстановления](disaster-recovery.md).
7. **Приёмка.** Новый телефон со старым выключенным, вход по почте и восстановление без отдельного ключа. Android → PWA и обратно, ZIP с исходным Android-вложением, совпадение записей, настроек, заметок и идентификаторов. Проверить перезапуск после копирования, потерю сети, повтор `finalize`, испорченный файл, запасную версию, ошибку между загрузкой и обновлением каталога, разошедшиеся устройства, отказ в доступе для чужого аккаунта и гостя. В `web/tests/web-archive.test.ts` проверить формат и очистку временных данных комнаты. В `web/e2e/archive.spec.ts` пройти предпросмотр, локальный откат и перезапуск. Запустить серверные тесты двумя аккаунтами, включая удаление и скачивание.

## C. Онлайн-комната с паритетом локальной · Medium для React, High для протокола

**Сценарий.** Один лучник с Android или PWA создаёт комнату через интернет. Остальные входят по ссылке, QR или коду. Тренер и лучники могут находиться в разных сетях. Стрелок ведёт свой раунд и серию в собственном темпе, отслеживая остальных в той же таблице. Гость вводит только отображаемое имя. Активная локальная комната и личный ввод продолжают работать по прежнему маршруту.

1. **Вход.** В существующем входе групповой тренировки предложить «Локальная сеть» и «Через интернет». В режиме интернета создание запрашивает вход в аккаунт, если его ещё нет. При открытии приглашения показать название и кнопку «Войти гостем», для авторизованного участника — имя профиля с возможностью уточнить отображаемое имя комнаты. Сохранить предсказуемое поведение при существующей активной тренировке: пользователь сам решает, приостановить её или вернуться, журнал сохраняет стрелы. `FS1` направляется в прежний транспорт, интернет-приглашение `FS2` содержит ID комнаты и случайный токен в коде или фрагменте URL. Сервер хранит хеш токена. Разбирать только приглашение установленного формата и известного адреса. Приглашения и авторизационные данные не копировать в общий результат, архив или лог.
2. **Результаты и UI.** Вынести выбор транспорта в `group-room-membership.ts`, адаптеры держать отдельными от `group-series.ts`. Переиспользовать `LocalRoomProbe.tsx` как текущую форму входа или общий экран комнаты, `GroupLeaderboard.tsx`, `group-leaderboard.ts`, `room-result-card.ts`, `room-achievements.ts`, `RoomHelp.tsx` и точки входа в `main.tsx`. Поддержать просмотр участников с именами и типами лука, классические очки, CG3 и PG1 из действующей реализации, выбор серии и условий, фильтры, историю, PNG и действующие групповые награды по тем же условиям. Для 40 см и «Светофора» сохранять действующие профили мишеней. В историю помещать собственную тренировку, название комнаты и последний полученный снимок. Чужой дневник, координаты отдельных стрел, заметки и комплекты не отправляются. Для зачёта передаётся тот же агрегат закрытой серии, что и в локальной комнате.
3. **Серверный контракт.** `create` фиксирует ID, имя, версию протокола и статус `open`; `preview` после проверки приглашения отдаёт только краткое описание; `join` связывает участника с аккаунтом или анонимной сессией и возвращает стабильный `entryId`; `publish` принимает собственные ревизии; `sync` выдаёт разрешённый снимок или изменения; `finalize` и `close` доступны создателю. В серверном чеке отдельно сверять полномочие на комнату и запись. Создатель управляет жизненным циклом и не правит чужие серии. Синхронно валидировать поля и допустимые профили по `isGroupSeriesRevision` и правилам Android-узла. Хранить точную `revision`, стабильные `endId` и `ordinal`, плюс монотонную версию комнаты. В транзакции проверять состояние комнаты и уникальность ключей `(room, entry, endId)` и `(room, entry, ordinal)`. Та же ревизия с тем же payload возвращает прошлое подтверждение, та же с другим — конфликт, старая получает актуальную принятую ревизию. Удаление серии — штатная ревизия с `result: null`, порядок сохраняется. Фиксация и запись серии сериализуются на сервере. Подтверждение выдаётся после commit, событие веб-сокета служит сигналом перечитать данные.
4. **Обрыв, остановка и возврат.** Использовать существующую локальную очередь `GroupSeriesJournal` и `flushGroupSeries`. В момент обрыва метки сохраняются сразу, в комнате видно «Ожидает отправки» и время последнего обмена. После подключения или возврата в приложение запросить `sync(sinceVersion)`, догнать актуальные данные и повторить очередь с серверной дедупликацией. Приватный Realtime даёт уведомления о версии, объединять всплески до одного сигнала в секунду, при недоступности веб-сокета периодически подтягивать данные только пока открыт экран комнаты. При разрыве между серверной фиксацией и ACK повтор возвращает ту же принятую ревизию. Гость после простого закрытия приложения возвращается по сохранённой сессии. После очистки данных может снова войти по действующему приглашению новым участником. Аккаунт может вернуться с другого устройства к той же серверной записи, при конфликте правки нужна свежая ревизия.
5. **Финализация и срок пилота.** Пока создатель выключил телефон, серверная комната остаётся открыта. Повтор `finalize` выдаёт тот же неизменяемый итог. «Зафиксировать» включает уже подтверждённые серии, интерфейс предупреждает про известные ожидающие записи. После «Закрыть» обмен прекращается. Открытая комната пилота действует 24 часа, чтение зафиксированного итога участниками доступно 7 дней с момента финализации, затем серверную копию удаляет плановая задача. Ранее загруженные результаты остаются в локальной истории. После терминального ответа серверу локальная очередь больше не повторяет отклонённые операции, а экран показывает, что серия осталась в личном дневнике без подтверждения комнаты. Эти правила коротко добавить в подсказку `RoomHelp.tsx` для режима интернета. [Приватные каналы Realtime](https://supabase.com/docs/guides/realtime/authorization)
6. **Приёмка.** Для одной и той же обезличенной последовательности серий LAN и онлайн выдают одинаковые зачёты и экспорт. Контрольные сценарии: Android-организатор, браузер-организатор, гость без аккаунта, участник с аккаунтом, две разные сети, разное число серий и раундов, обрыв до ACK и после ACK, повторяющаяся и устаревшая ревизия, отключение поддерживающего телефона, вход по истёкшему приглашению, завершение одновременно с отправкой, отсутствие доступа для постороннего к `sync` и к чужому участнику. Запускать существующие браузерные тесты LAN и `group-series` плюс серверный тест фиксации. Сначала пилот на 2–3 устройствах, затем нагрузочные ступени 10/25/50 клиентов. Измерять p95 времени до видимости серии при одновременном вводе и сверять лимиты соединений и трафика. Число 50 — цель проверки, вывод о поддерживаемом размере комнаты делается по результатам.

## Общая приёмка

- Использовать локальный и пилотный контуры перед включением публичных флагов. В React прогнать тесты логики, сборку и затронутые браузерные сценарии. Для новых серверных функций проверить контракт, разграничение и повтор операций на изолированной базе.
- При отключённом облачном контуре приложение продолжает личную тренировку, открывает дневник и позволяет экспортировать ZIP. Локальная комната и её Android-мост работают своим путём. На физическом устройстве проверить отдельно уведомление, восстановление с выключенным старым телефоном и обмен по двум сетям. Сохранять фактический итог каждого прогона.
- Выпуск Android и PWA проходит через единый существующий процесс. Отдельно проверить, что новая PWA читает ранее сохранённый кэш, обновляется и снова открывается офлайн. Реализация и публикация этого плана относятся к следующей задаче.
