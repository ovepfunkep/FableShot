# Схемы и безопасные миграции

Текущая схема **9** (2 ноября 2026), миграции 1→2→3→4→5→6→7→8→9. Последняя 8→9 только добавляет diary_notes и индексы. Проверена на изолированных базах и проверенной копии личного дневника; после установки сравнение всех полей 16 прежних таблиц точное. [Проверки 0.14.0](../verification/android-0.14.0.md). Разделы ниже описывают историческое основание, не текущий статус.

## Исходная схема и границы

Источник истины для схемы 1 — экспорт `android/app/schemas/app.fableshot.android.data.PracticeDatabase/1.json` и реальные Entity. JSON нельзя вручную переписать под новую модель: он нужен для воспроизведения старой установки.

Сейчас sessions содержат distanceMeters/targetDiameterMm/arrowsPerEnd/profileId; ends ссылаются прямо на sessions; shots имеют points, необязательные x/y, origin, createdAt и revision. Времени отдельных серий, часового пояса, типа лука и оригинального значения перед ручной правкой нет. Миграция их не придумывает.

Тесты F01 подтверждают нынешние транзакции и восстановление, а не изменение схемы. При переходе на версию 2 нужны новые миграционные тесты на экземплярах схемы 1.

## 1 → 2: преобразование по сущностям

- Каждый Session сохраняет ID/title/state/completedAt. `createdAtMs` и `startedAtMs` получают прежний startedAt: в прототипе это известный момент создания/начала учёта, не физической стрельбы. Источник времени — legacy_app_clock. Зона и календарная дата остаются null, если ранее не записаны.
- Новый Block создаётся один на старую Session, ordinal=0. ID детерминирован: name-based UUID от UTF-8 `fableshot:block:v2:<sessionId>`, алгоритм закрепляется тестом. Дистанция, диаметр, план и профиль переносятся без изменений.
- Для известного `practice-full-10-v1` создаётся неизменяемый снимок той же учебной геометрии. Оборудование — null; нельзя по названию тренировки угадывать лук. Неизвестный профиль не заменяется стандартным молча.
- End сохраняет ID/план, получает новый blockId и ordinal=number−1. closed переносится в state; createdAtMs/closedAtMs остаются null. Роль scored известна: разминка в прототипе не предлагалась.
- Shot сохраняет ID/endId/inputIndex/points/x/y/createdAt/revision. updatedAtMs — null, поскольку отдельно не хранилось.
- origin=target → scoreSource=target_computed; numeric → numeric_entry; manual → manual_edit. Известные парные координаты из этих путей → manual_target/known, иначе none/unknown. Неизвестный origin требует явного обработчика, не silent fallback.
- zoneCode: 0→M, 1..10→числовой код. X не выводится из 10: исходный учебный профиль X не поддерживал. automaticPoints/ruleVersion остаются null в миграции; автоматическое предложение можно пересчитать отдельно, не выдавая его за сохранённый исторический факт.
- Для известной точки faceId=main; известные внешние M с координатами сохраняются. Numeric M с null остаётся без положения. В прототипе MyTargets не импортировался, поэтому пользовательские данные v1 не требуют эвристики «все нулевые точки — промахи».
- UnscoredCount не создаются: режим без оценки ранее отсутствовал. Новые поля revision и прочие значения по умолчанию задаются явно; нет новых Shot за пустые места.

## Порядок реализации SQL

1. Поднять версию Entity/Database только вместе с реализацией Migration(1,2), экспортом `2.json`, новыми запросами/репозиторием и их тестами. Не выпускать APK, где модель и чтение условий расходятся.
2. До изменения DDL проверить исходные профили/источники/связи, планы, плотный порядок и пары конечных координат. Затем внутри одной транзакции переименовать **старые** таблицы в порядке shots → ends → sessions в *_legacy.
3. Создать новые таблицы сразу с окончательными именами и FK sessions → blocks → ends → shots / unscored_counts, а также mutation_receipts. Скопировать строки из *_legacy с преобразованием выше.
4. Сверить число строк и сумму очков; удалить старые *_legacy в порядке shots → ends → sessions. Новые таблицы ссылаются только на окончательные новые имена, поэтому удаление старых не затрагивает их.
5. После освобождения имён старых индексов создать итоговые индексы; `PRAGMA foreign_key_check` должен вернуть пустой результат.
6. Room проверяет итоговую схему по экспорту; транзакция завершается только после успеха всех проверок. Не отключать FK внутри уже начатой транзакции и не использовать destructive fallback.

Алгоритм соответствует реализованному DDL/экспорту JournalDatabase/2.json. Первоначальный вариант «*_new → rename» действительно провалился на Xiaomi: ссылка FK осталась на sessions_new. Ошибку обнаружили на искусственной базе, исправили порядком выше; четыре миграционные проверки затем прошли. Проверка минимального API 29 ещё впереди.

## Копия перед реальным обновлением

Сначала прогон на искусственных экземплярах старой схемы и отдельной копии, а не сразу на единственном пользовательском дневнике. До первой установки мигрирующей версии подготовить и проверить восстанавливаемую локальную копию текущей базы.

SQLite может держать подтверждённые изменения в WAL. Нельзя просто копировать один открытый `fableshot.db` и считать копию полной. Предпочтительный путь для данного прототипа: остановить процесс, сохранить согласованный комплект db/wal/shm при наличии, открыть **копию** для проверки/checkpoint и проверить читаемость/счётчики. Более поздний архив приложения создаётся средствами собственного согласованного экспорта.

Личная резервная копия лежит в исключённой из Git локальной папке; содержимое/персональные строки не печатаются в общий журнал. Для F01 реальные файлы дневника не копировались и не менялись — использованы только тестовые базы.

Старый APK не умеет читать новую схему. Откат APK без восстановления согласованной старой копии не является безопасным откатом. Не применять downgrade/destructive migration к пользовательским данным.

## Обязательная матрица проверок 1 → 2

- Пустая база; пустая активная Session; одна полная/неполная серия; несколько завершённых занятий и одна активная.
- Координаты центра, числовые очки без положения, M без положения, внешний M с известной точкой, ручная оценка, отличная от геометрии; совпадающие реальные стрелы.
- Несколько серий, 3/6 стрел, планы и closed, исходные IDs/inputIndex/createdAt/revision без изменений.
- Неизвестный профиль/origin, повреждённые связи/непарные координаты/ошибочный порядок: отказ без подмены данных.
- Точные суммы/число Shot до и после, корректность нового Block и снимка геометрии, сохранение текущей активной серии.
- Room schema validation, foreign_key_check, повторное открытие после миграции, прежние данные через новые repository/Flow.
- Искусственный сбой посередине: старое состояние остаётся читаемым; повторный успешный запуск не создаёт дополнительные Block.
- Проверка копии/восстановления и повторная установка подписанной сборки с настоящей миграцией. До этого нельзя объявлять безопасным обновление на новой модели.

## Следующие версии

### Journal 14 → 15, пакет 0.29.0

`ALTER TABLE shots ADD COLUMN shaftDiameterMm REAL DEFAULT NULL`. Старые строки, очки, ревизии, происхождение и timestamps не изменяются. Обновляется только Room identity/schema; новые отметки используют явно зафиксированный диаметр. Старые квитанции правок с null-диаметром сохраняют прежний hash-контракт. Миграция проверяется на искусственной базе 14 и на копиях обоих установленных дневников; сведения об актуальной установке находятся в очереди, а не выводятся из наличия исходников.

После ядра новые подсистемы добавляются по этапам: импорт/корзина и перенос, метрики/снимки баз, техника/фото/цели, затем сеть. Номера фиксируются по реально выпущенным схемам; заранее резервировать каждую цифру не требуется.

Для каждой версии: Entity + миграция + экспорт схемы + данные прежнего формата + проверки инвариантов + описание для пользователя. Новые расчёты получают версии формул независимо от версии SQL; смена формулы не переписывает первичные Shot.
